3.1 정적 테스팅 기초
FL-3.1.1 (K1) 정적 테스팅으로 검토할 수 있는 작업 산출물 유형을 인식할 수 있다
명세서, 소스콛, 테스트 계획서, 케이스, 차터, 백로그, 프로젝트 문서, 계약서, 모델

FL-3.1.2 (K2) 정적 테스팅의 가치를 설명할 수 있다
조기 테스팅 원리를 지킬 수 있음, 개발수명주기 초반에 수행되므로 많은 이해관계자가 참가, 리뷰 구축 비용이 들지만 프로젝트 후반의 결함 수정 시간, 노력이 준다. 일부 결함은 동적 테스팅보다 효율적, 정적 테스팅으로만 식별가능

FL-3.1.3 (K2) 정적 테스팅과 동적 테스팅을 비교하고 대조할 수 있다
한 가지로만 식별 가능한 결함 있음
정적은 직접 식별, 동적은 장애를 일으킨 후 결함을 후속 분석
정적은 비실행 작업 산출물에도 적용 가능, 동적은 실행 가능한 작업 산출물만 적용
정적은 코드 실행에 의존 안 하는 품질 특성(유지보수)에 사용 가능, 동적은 코드 실행에 의존적인 품질 특성(성능효율)을 측정하는데 사용

요구사항, 설계, 코딩, 포준 위반, 명세, 보안 취약, 테스트 베이시스가 대표적인 효율 정적 테스팅

3.2 피드백과 리뷰 프로세스
FL-3.2.1 (K1) 이해관계자 피드백을 조기에 자주 받을 때의 이점을 식별할 수 있다
잠재적 품질 문제를 조기 파악 가능

FL-3.2.2 (K2) 리뷰 프로세스에서 수행하는 활동을 요약할 수 있다
계획, 리뷰 착수, 개별 리뷰, 논의 분석, 수정 보고
리뷰 중 확인한 이상이 반드시 결함은 아니므로 모두 분석하고 논의할 필요 있음
참가자들은 리뷰한 작업 산출물에 대한 품질 수준과 후속 조치도 결정, 후속 리뷰도 필요
결함 보고서 작성으로 후속 조치의 추적성

FL-3.2.3 (K1) 리뷰를 수행할 때 주요 역할별로 어떤 책임이 부여되는지 상기할 수 있다
관리자(리뷰 결정), 저자(작업 산출물 작성, 수정), 중재자, 서기(리뷰어로부터 이상 수집, 회의 중 새로운 이상 사항, 정보 기록), 리뷰어, 리뷰 리더

FL-3.2.4 (K2) 다양한 리뷰 유형을 비교하고 대조할 수 있다
비공식 리뷰(정의된 프로세스는 없음), 워크쓰루(저자가 리더, 리뷰어는 워크쓰루전 개별 리뷰도 가능), 기술 리뷰(리뷰어는 기술적 자격이 필요, 중재자가 리더, 기술 문제에 대한 합의, 아이디어 창출), 인스펙션(공식적 리뷰, 이상 사항을 최대한 많이 찾는게 목적, 매트릭을 수집해 sdlc 개선, 저자나 리뷰 리더가 서기가 될 수 없음
)
FL-3.2.5 (K1) 성공적인 리뷰에 기여하는 요소를 상기할 수 있다
측정 가능한 완료 조건, 참가자의 평가가 목적이 되어선 안됨
주어진 목표를 달성 하면서 정황에 맞는 리뷰 유형을 선택
작은 단위로 리뷰
이해관계자와 저자에게 리뷰 피드백 제공
리뷰 프로세스를 관리층이 지원
모든 참가자에게 역할에 대한 적절한 교육
회의에 퍼실리테이션 적용 (참여자 중심, 브레인스토밍)

4.1 테스트 기법 개요
FL-4.1.1 (K2) 블랙박스 테스트 기법, 화이트박스 테스트 기법, 경험 기반 테스트 기법을 구별할 수 있다
블랙박스 - 명시된 동작에 대한 분석, 구현이 바껴도 동작이 동일하면 여전히 유효
화이트박스 - 내부 구조와 처리에 대한 분석, 소프트웨어 설계 방식에 의존하므로 테스트 대상의 설계나 구현이 끝난후 만들어짐
경험 기반 - 테스터의 능력에 따라 잘라짐, 다른 테스트 기법으로 식별 못 하는 결함이 식별되므로 보완하는 느낌

4.2 블랙박스 테스트 기법
FL-4.2.1 (K3) 동등 분할을 사용해 테스트 케이스를 도출할 수 있다
입력, 출력, 형상 항목, 내부 값, 시간, 인터페이스 매개변수 등 모든 데이터 요소에 식별 가능(분할은 겹치지 않아야하고, 공집합인 경우는 없음)
모든 요소를 동일한 방식으로 처리한다는 가정하에 데이터를 분할
각 분할에 하나의 테스트

FL-4.2.2 (K3) 경계값 분석을 사용해 테스트 케이스를 도출할 수 있다
동등 분할의 (최솟값, 최댓값) 경계값 실행을 기반, 정렬된 분할에만 사용가능, 두 값이 같은 분할일 경우 둘 사이 값도 해당 분할에 속해야함
두 개 선택은 인접분할에 가장 가까운 값, 세 개 선택은 이웃한 양쪽의 값
세 개 선택이 엄격하나 오래 걸림

FL-4.2.3 (K3) 결정 테이블 테스팅을 사용해 테스트 케이스를 도출할 수 있다
서로 다른 조건 조합으로 달라지는 결과를 요구사항이 제대로 구현했는지
비지니스 규칙과 같은 복잡한 논리 기록에 효과적
행은 조건과 결과를 서술, 열은 결정 규칙

| 조건 / 규칙 | R1 | R2 | R3 | R4 |
|---|---|---|---|---|
| C1 계정 존재 | T | T | T | F |
| C2 비밀번호 일치 | T | F | - | N/A |
| C3 계정 잠금 여부 | F | F | T | N/A |
| | | | | |
| A1 로그인 성공 | X |  |  |  |
| A2 로그인 실패 |  | X |  | X |
| A3 계정 잠금 안내 |  |  | X |  |

T(조건충족), F(조건충족X), -(조건 값이 결과에 영향X) N/A(조건 실행 불가능
X(결과 동작 불가능), () (동작이 발생하지 않아야함)

FL-4.2.4 (K3) 상태 전이 테스팅을 사용해 테스트 케이스를 도출할 수 있다
유효한 상태 전이로 시스템 동작을 모델링, 전이는 즉각적인 하나의 이벤트에 의함, 별도의 가드 조건이 있을 수 있고, 어떤 동작으로 연결되기도 함

| TC | 현재 상태 | 이벤트 | 예상 상태 |
|---|---|---|---|
| TC1 | 정상 | 로그인 실패 | 실패 1회 |
| TC2 | 실패 1회 | 로그인 실패 | 실패 2회 |
| TC3 | 실패 2회 | 로그인 실패 | 계정 잠금 |
| TC4 | 실패 1회 | 로그인 성공 | 정상 |
| TC5 | 실패 2회 | 로그인 성공 | 정상 |

모든 상태 - 존재하는 모든 예상 상태 테스트
유효 전이* - 설계상 이동 가능한 상태만 (충족 최소 기준)
모든 전이 - 모든 상태간 이동 테스트

4.3 화이트박스 테스트 기법
FL-4.3.1 (K2) 구문 테스팅을 설명할 수 있다
커버리지 항목은 실행 가능한 구문, 구문 내 모든 코드를 적어도 한번은 실행
그러나 구문 커버리지가 모든 결정 논리를 테스트 했다고 보장 x

ex) bool문에 참값만 실행된 경우

FL-4.3.2 (K2) 분기 테스팅을 설명할 수 있다
제어 흐름 그래프에서 두 노드간 제어의 이동으로 테스트 대상의 소스 코드 구문 실행 가능 순서를 보여줌, 제어의 이동은 조건 없이, 또는 조건에 따라 이루어 진다
코드의 분기를 실행하는 테스트 케이스 설계

ex) bool문의 참 거짓 모두 테스트

그래서 분기는 구문을 포함하나 그 반대는 불가

FL-4.3.3 (K2) 화이트박스 테스팅의 가치를 설명할 수 있다
테스트 중 소프트웨어 구현을 고려하므로 명세가 모호하거나 불완전해도 결함을 쉽게 감지
블랙박스 만으로 실제 코드 커버리지 측정치를 얻을 수 없음, 화이트박스로 객관적인 커버리지 측정값을 제공, 신뢰도 상승

4.4 경험 기반 테스트 기법
FL-4.4.1 (K2) 오류 추정을 설명할 수 있다
테스터 지식을 기반, 결함 예측(과거 동작, 자주 일어나는 오류, 유사 제품의 장애 유형)

FL-4.4.2 (K2) 탐색적 테스팅을 설명할 수 있다
테스트의 설계, 실행, 평가를 동시에
시간을 정해놓은 세션 기반 테스팅도 사용 하기도, 이때 테스트 목적은 상위 수준의 테스트 컨디션으로 취급 가능
명세가 부족하거나 부적합, 시간적 압방에 유용

FL-4.4.3 (K2) 체크리스트 기반 테스팅을 설명할 수 있다
체크리스트로 테스트 컨디션을 설계, 구현, 실행, 이때 자동 점검 항목, 시작 조건, 종료 조건에 적합한 항목은 체크리스트에서 제외
갈수록 체크리스트는 효과가 떨어짐, 새로운 결함으로 항목 추가가 빈번함, 결함 분석 기반으로 정기적 업데이트가 필요

4.5. 협업 기반 테스트 접근법
FL-4.5.1 (K2) 개발자 및 업무 대표자와 협업해 사용자 스토리를 작성하는 방법을 설명할 수 있다
사용자 스토리 - 유저에게 가치를 제공하는 기능
3C(카드(사용자 스토리를 설명하는 매체), 대화, 확인)
일반적인 형식 "역할 - 목표 달성 - 달성으로 얻는 비지니스 가치를 추구" 이후 인수 조건이 뒤따름

FL-4.5.2 (K2) 인수 조건을 작성하는 여러가지 방법을 분류할 수 있다
3C중 스토리 구현 결과를 이해관계자와의 '대화'로 충족되는 조건
시나리오 기반(given/when/then), 규칙 기반이 있으며 이 형식으로 문서화됨

FL-4.5.3 (K3) 인수 테스트 주도 개발(ATDD)을 사용해 테스트 케이스를 도출할 수 있다
테스트 우선 접근법, 사용자 스토리 구현 전 만들어짐, 자동 수동 상관없음
첫 번째로는 긍정/유효 테스트, 그 다음은 비유효/부정 테스트를 수행
비기능 품질 특성을 포함한 자연어 문장으로 구현
테스트 케이스는 사용자 스토리의 모든 특성을 다뤄야

5장 학습 목표
5.1 테스트 계획
FL-5.1.1 (K2) 테스트 계획서의 목적과 내용을 예를 들어 설명할 수 있다
목적 달성을 위한 방법과 일정 문서화, 테스트 활동 기준에 도움, 의사소통 수단, 테스트 정책 및 전략의 준수함

테스팅 정황, 가정 및 제약 사항, 이해관계자, 의사소통, 리스크 목록, 접근법, 예산 및 일정

FL-5.1.2 (K1) 테스터가 반복 주기와 릴리스 계획에 가치를 더하는 방법을 인식할 수 있다
릴리스 계획은 제품 백로그의 (재)정의, 테스트 접근법과 계획의 기반
사용자 스토리와 인수 조건의 작성, 품질 분석에 참여, 테스트 노력, 접근법, 릴리스까지 계획
반복 주기 계획은 개별 반복 주기를 계획으로 반복 주기 백로그와 관련
구체적인 리스크 분석에 참여, 사용자 스토리의 용이성, 업무 단위로 분류, 테스트 대상의 기능 및 비기능적 측면 식별하고 구체화

FL-5.1.3 (K2) 시작 조건과 완료 조건을 비교 및 대조할 수 있다
시작 조건 - 어떤 활동 수행에 필요한 전제 조건
자원 가용성, 테스트웨어 가용성, 대상의 초기 품질
완료 조건 - 특정 활동 종료를 선언하기 위해 달성이 필요한 조건
달성 커버리지 수준, 미해결 결함 수와 밀도, 실패한 테스트 케이스 수, 예/아니오로 판단되는 기준

FL-5.1.4 (K3) 필요한 테스트 노력의 계산을 위해 추정 기법을 활용할 수 있다
비율 기반 추정 - 이전 수치로 유사 프로젝트를 위한 표준 비율을 도출
외삽법 - 메트릭 기반, 빠른 측정으로 남은 노력의 근사치 추정 가능, sdlc에 적합
와이드밴드 델파이 - 전문가 경험 기반, 각 전문가 독립적으로 추정, 합의할때까지
3점 추정 - 전문가가 낙관, 확률적, 비관 수치 3개를 도출, (a+4*b+b)/6 로 표준편차 도출

FL-5.1.5 (K3) 테스트 케이스에 우선순위를 적용할 수 있다
리스크 기반 - 리스크 분석 결과에 따라 순서 결정
커버리지 기반 - 높은 커버리지의 테스트 케이스부터

5.2 리스크 관리
FL-5.2.1 (K1) 리스크 발생 가능성과 리스크 영향도를 활용해 리스크 수준을 식별할 수 있다
리스크 가능성 - 발생 확률 (0 - 1)
리스크 영향 - 발생시 피해

FL-5.2.2 (K2) 프로젝트 리스크와 제품 리스크를 구별할 수 있다
프로젝트 리스크 - 관리 및 제어, 조직, 인력, 기술적, 공급업체
제품 리스크 - 사용자 불만족, 매출, 신뢰, 유지보수

FL-5.2.3 (K2) 제품 리스크 분석이 철저함과 테스트 범위에 미치는 영향에 대해 설명할 수 있다
전체 리스크 수준의 최소화 목표, sdlc 초기에 시작
리스크 식별 - 포괄적 리스크 목록 생성, 우선순위를 결정 조치를 제안
리스크 평가 - 정량적, 정성적, 혼합 접근법 사용, 정량적은 발생 가능성 * 영향의 값, 정성적은 리스크 행렬로 리스크 수준 판단

수행 테스트 범위 결정 및 테스트 레벨, 유형, 기법, 커버리지 결정
중요 결함 식별을 위해 우선순위 지정
리스크 최소화를 위해 테스팅 외 다른 활동도 판단

FL-5.2.4 (K2) 분석한 제품 리스크에 대응해 어떤 조치를 취할 수 있는지 설명할 수 있다
적절한 경험과 기술의 테스터, 테스팅 독립성, 리뷰 및 정적 분석, 적절한 테스트 기법과 커버리지 수준 적용, 적절한 테스트 유형 적용, 리그레션 테스팅을 포함한 동적 테스팅 수행

5.3 테스트 모니터링, 테스트 제어, 테스트 완료
FL-5.3.1 (K1) 테스팅에 사용하는 메트릭을 상기할 수 있다
프로세스나 제품의 상태를 수치로 측정하는 지표
테스트 활동의 효과를 보여주기 위해 수집
완료율, 사용율, 진행률, 진행 케이스 수, 시간, 비용

FL-5.3.2 (K2) 테스트 보고서의 목적, 내용, 대상을 요약할 수 있다
테스팅 도중, 이후에 정보를 요약하고 전달하는 활동, 지속적인 테스트 제어 및 정보 제공, 이해관계자를 위해 정기적 보고서 작성
기간, 진행상황, 방해요소, 대응, 메트릭, 신규, 변경 리스크, 다음 주기 테스팅
완료 보고서 - 완료 조건 충족 상황 후 완료 활동 중 작성
요약, 원래 계획, 편차, 완화 되지 않은 리스크, 수정 안된 결함, 교훈

FL-5.3.3 (K2) 테스팅 상황을 전달하는 방법을 예를 들어 설명할 수 있다
대화 대시보드 통신채널 온라인문서, 보고서

5.4 형상 관리
FL-5.4.1 (K2) 형상 관리가 테스팅을 어떻게 지원하는지 요약할 수 있다
작업 산출물을 형상 항목으로 식별 제어 추적하는 지침 활동
형상 항목이 테스팅용으로 승인 될 경우 베이스라인이 되며 공식적인 변경 프로세스로만 수정가능
테스트 항목의 형상 항목은 고유 식별자로 버전 관리되어 전체 프로세스는 추적성이 유지
CI/CD 상 테스팅은 일반적으로 자동화 데브옵스 파이프라인으로 구현되며 여기 형상 관리도 포함됨

5.5 결함 관리
FL-5.5.1 (K3) 결함 보고서를 작성할 수 있다

작업 결과의 품질을 추적할 수단 제공
개선을 위한 아이디어 제공

동적 테스팅 시 고유 식별자, 이상 사항 요약 제목, 날짜, 작성자, 대상 및 환경 식별, 결함의 정황, 발견한 절차 및 테스트 로그, 스크린샷 류의 재현 및 해결에 필요한 정보, 기대결과, 실제결과, 심각도, 수정 우선순위, 결함 상태, 참조 사항
