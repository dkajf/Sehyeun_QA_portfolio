테스트 대상의 결함 식별, 품질을 평가
장애 유발, 결함 식별
리스크 완화, 명세 충족 여부의 베리피케이션, 고객 요구사항 준수 여부의 벨리데이션

FL-1.1.2 (K2) 테스팅과 디버깅을 구별할 수 있다
테스팅 이후 디버깅
(동적)장애 유발 - 분석(재현) - 수정
(정적)직접 색출 - 수정 (재현x)

1.2 테스팅이 왜 필요한가?
FL-1.2.1 (K2) 테스팅이 필요한 이유를 예를 들어 설명할 수 있다
효율적인 비용으로 품질 향상

FL-1.2.2 (K1) 테스팅과 품질 보증의 관계를 상기할 수 있다
테스팅 - 제품 지향적, 교정 접근법 사용
품질 보증 - 프로세스 중심의 예방 접근법
테스팅 결과는 둘 다 사용

FL-1.2.3 (K2) 근본 원인, 오류, 결함, 장애를 구별할 수 있다
사람의 오류 - 결함 발생 - 시스템 장애
근본 원인 - 근본적인 이유(오류로 이어지는 상황)
근본 원인 분석은 보통 장애가 발생하거나, 결함을 식별한 경우 수행

1.3 테스팅 원리
FL-1.3.1 (K2) 테스팅의 7가지 원리를 설명할 수 있다
테스팅은 결함의 존재를 밝히는 활동이지, 결함이 없음을 증명하지는 않는다
완벽한 테스팅은 불가
조기 테스팅으로 시간과 비용 절약 가능
결함은 집중된다
테스트 효과는 줄어든다
테스팅은 정황에 의존적이다
결함-부재는 궤변이다

1.4 테스트 활동, 테스트웨어, 테스트 역할
FL-1.4.1 (K2) 다양한 테스트 활동과 관련된 업무를 설명할 수 있다
테스트 계획 - 목적을 가장 잘 달성할 수 있는 접근법
테스트 모니터링, 제어 - 지속적으로 테스트 활동을 점검 실제 진행 상황을 계획과 비교
테스트 분석 - 테스트 베이시스를 분석해 테스트 가능한 기능을 식별
테스트 설계 - 테스트 컨디션을 구체화, 커버리지 항목의 식별을 포함(어떻게 테스트 할 것인가)
테스트 구현 - 테스트 웨어 생성 및 획득, 테스트 절차로 묶을 수 있으며 테스트 스위트로 조합하는 경우도 많다
테스트 실행 - 테스트를 수동 및 자동으로 수행, 실제 결과와 기대 결과를 비교
테스트 완료 - 프로젝트 마일스톤 안에서 수행, 해결되지 않은 결함의 변경 요청서, 백로그 생성, 보고서 전달

FL-1.4.2 (K2) 정황이 테스트 프로세스에 미치는 영향을 설명할 수 있다
테스트는 단독으로 수행되지 않고 많은 이해관계자들이 존재
최종적으로 이해관계자의 비지니스 목표 달성을 지원하는 것

FL-1.4.3 (K2) 테스트 활동을 지원하는 테스트웨어를 구분할 수 있다
테스트 설계 작업 산출물 - (우선순위 포함)테스트 케이스, 테스트 차터, 커버리지 항목, 테스트 데이터 요구사항, 테스트 환경 요구사항
테스트 구현 작업 산출물 - 테스트 절차, 수동 및 자동 테스트 스크립트, 테스트 스위트, 테스트 데이터, 테스트 실행 일정, 테스트 환경 요소. 테스트 환경 요소의 예로는 스텁(stubs), 드라이버, 시뮬레이터, 서비스 가상화

FL-1.4.4 (K2) 추적성을 유지하는 것의 가치를 설명할 수 있다
정확한 추적성은 커버리지 평가를 지원, 측정 가능한 커버리지 조건이 테스트 베이시스에 정의 됐다면 테스트 목적의 핵심 성과 지표로 활용 가능

FL-1.4.5 (K2) 테스팅에 참여하는 다양한 역할을 비교할 수 있다
테스트 관리 - 계획 제어 완료
테스트 - 분석 설계 구현 실행
한사람이 둘다 할 수 있다

1.5 테스팅 필수 기술 및 모범 사례
FL-1.5.1 (K2) 테스팅에 필요한 보편적인 기술의 예를 제시할 수 있다

FL-1.5.2 (K1) 전체 팀 접근법의 장점을 상기할 수 있다

이에 협업이 강화되고 시너지 창출

그러나 협업과 의사소통이 어려울 수 있어 케어가 필요

2.1 소프트웨어 개발수명주기(SDLC)에서의 테스팅
FL-2.1.1 (K2) 소프트웨어 개발수명주기(SDLC)가 또는 선택된 소프트웨어 개발수명주기가 테스팅에 미치는 영향을 설명할 수 있다
SDLC에 따라 시기, 방법, 자동화 수준, 테스터 역할이 다르므로 테스트 전략도 조정되어야한다

FL-2.1.2 (K1) 모든 소프트웨어 개발수명주기(SDLC)에 적용되는 좋은 테스팅 프랙티스를 상기할 수 있다
모든 개발 활동이 품질 제어의 대상
구체적이고 독립적인 테스트 목적으로 중복은 피하고 적절히 포괄적인 테스팅
특정 테스트 레벨을 위한 분석과 설계를 SDLC에 상응하는 개발단계에 시작해 조기 테스팅 원칙 준수
무서 초안이 가용한 즉시 리뷰에 참여, 시프트 레프트 전략을 지원

FL-2.1.3 (K1) 개발에서 테스트 우선 접근법의 예를 들 수 있다
TDD - 테스트 케이스를 통해 코딩 주도 (테스트 - 코딩 - 리팩토링)
ATDD - 인수 조건에서 테스트 도출 (테스트는 해당 테스트를 만족하는 개발 전에 작성)
BDD - 자연어로 이해관계자를 위한 테스트 케이스 (GIVEN/WHEN/THEN)
이후 테스트 케이스는 자동으로 실행 가능하게 변환

FL-2.1.4 (K2) DevOps가 테스팅에 미치는 영향을 요약할 수 있다
개발과 운영이 협력해 목표 달성을 위한 시너지 창출
기술 프랙티스를 장려하며 배포 파이프라인을 통해 높은 품질의 코드를 빠르게 빌드 테스트 릴리즈
 - 빠른 피드백과 지속적 통합은 시프트 레프트 테스팅 접근법을 장려
 - 자동화 프로세스 장려
 - 리그레이션 발생 리스크가 최소화

 - 파이프라인을 정의하고 설정해야
 - 지속적 배포 도구를 유지보수
 - 테스트 자동화를 위해 추가 자원 및 유지보수가 필요

높은 수준의 테스팅 자동화가 되나 수동 테스팅은 여전히 필요

FL-2.1.5 (K2) 시프트 레프트 접근법을 설명할 수 있다

2.2 테스트 레벨과 테스트 유형
FL-2.2.1 (K2) 테스트 레벨을 구별할 수 있다
함께 구성하고 관리하는 테스트 활동 집합

컴포넌트 테스팅 - 컴포넌트의 개별적 테스트, 구체적인 지원수단이 필요, 개발자가 자신의 개발 환경에서 수행
콤포넌트 통합 테스팅 - 컴포넌트 간의 인터페이스와 상호작용을 테스트(통합 전략에 따라 달라짐)
시스템 테스팅 - 전체 시스템, 제품의 동작과 기능에 중점, 비기능 품질 특성 포함, 독립된 테스트팀이 주로 수행하며 시스템 명세와 관련있음
시스템 통합 테스팅 - 다른 시스템, 외부 서비스와의 인터페이스를 테스트, 가급적 운영 환경과 유사히
인수 테스팅 - 밸리데이션, 사용자의 비지니스에 충족하는지, 실제 사용자가 수행하는 것이 이상적

FL-2.2.2 (K2) 테스트 유형을 구별할 수 있다
기능 테스팅 - 컴포넌트, 시스템이 수행, 테스트 대상이 무엇을 해야하는지 의미
비기능 테스팅 - 시스템이 얼마나 잘 작동하는지 테스트(비기능 품질 특성을 확인), 특수한 테스트 환경이 요구되는 경우도 있음
블랙박스 테스팅 - 명세 기반, 테스트 대상의 구조와 관련 없는 문서로 테스트 도출, 비교로 시스템의 동작을 확인
화이트박스 테스팅 - 내부 구조에서 테스트 도출

FL-2.2.3 (K2) 확인 테스팅을 리그레션 테스팅과 구별할 수 있다
확인 테스팅 - 해당 결함으로 실패한 모든 케이스 실행, 변경 사항을 위한 새로운 테스트 추가
리그레션 테스팅 - 변경으로 부정적인 영향을 확인(환경 포함), 영향도 분석 수행이 우선시, 리그레션 테스트 스위트는 반복적으로 실행, 자동화하기 적합

2.3 유지보수 테스팅
FL-2.3.1 (K2) 유지보수 테스팅과 유발요인을 요약할 수 있다
계획된, 계획되지않은 릴리스/배포와 모두 연관, 영향도 분석을 통해 다른 영역에 미칠 잠재적 영향을 결정에 참고 가능
변경하지 않은 시스템 영역에서 발생할 수 있는 리그레션를 확인하는 작업 모두 포함
시스템 단종시 보존 기간이 길면 보관(아카이빙) 테스팅이 필요할 수 있다
